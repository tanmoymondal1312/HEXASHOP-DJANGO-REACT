--------------------------------------------------------------------------------
1. WHAT THIS PROJECT IS
--------------------------------------------------------------------------------
HEXASHOP is a full-stack e-commerce store (dark, luxury-fashion themed) with:
  • A customer storefront (home, shop, product detail, cart, wishlist, auth)
  • A visual "Hero Builder Studio" — a Shopify/Framer-style page-builder where
    staff design the homepage hero slides with rich text and live preview
  • A Django admin + a custom staff panel
  • 65 seeded products (including a 50-item "Luxury Edit" collection with
    curated photography), categories, brands, variants and a full DB snapshot
    so the whole store can be cloned and run with data.

3. HIGH-LEVEL ARCHITECTURE
--------------------------------------------------------------------------------
  Browser
    │
    ├── Next.js (port 3000) — renders pages
    │     • Server Components fetch the Django API at build/request time
    │     • ISR: home page revalidates every 60s, plus ON-DEMAND revalidation
    │       (POST /api/revalidate) so Studio saves appear instantly
    │     • Client components handle cart, auth state, carousels, Studio
    │
    └── Django API (port 8000) — /api/v1/...
          • DRF viewsets/actions, JWT cookie auth, Redis caching
          • PostgreSQL for data, /media/ for images (dev)
          • Celery workers for async jobs

AUTH FLOW (cookie-based JWT):
  1. POST /api/v1/auth/login/  → sets HttpOnly cookies:
       access_token  (15 min, Path=/)
       refresh_token (7 days, Path=/api/v1/auth/token/refresh/)
  2. Axios sends cookies (withCredentials) on every request.
  3. On 401 the axios interceptor calls token/refresh once, replays the
     original request, and redirects to /auth/login if refresh fails.
     (The refresh call itself never triggers another refresh — deadlock guard.)
  4. /auth/me/ returns the user incl. is_staff — used to gate /studio.

                       ProductColor, ProductVariant, Review

                       categories, announcement, dashboard w/ page-view stats)

KEY PUBLIC API (all under /api/v1/):
  GET  /products/                     list w/ cursor pagination, filters, search (?q=)
  GET  /products/<slug>/              product detail
  GET  /products/viral/               top-18 by viral score
                                      (sold×3 + reviews×2 + views×0.1), cached 15 min
  GET  /products/featured/            up to 24 featured products EXCLUDING the
                                      viral top-18 (home sections never repeat)
  GET  /products/categories/          category tree
  GET  /settings/                     site settings (announcement, hero fallback)
  GET  /settings/hero-slides/         active hero slide JSON documents
  POST /auth/register|login|logout, GET/PATCH /auth/me/, POST /auth/token/refresh/
  GET/POST /cart/, /wishlist/, /notifications/...

STAFF-ONLY STUDIO API (IsAdminUser):
  CRUD /studio/hero-slides/           hero slide documents
  POST /studio/hero-slides/reorder/   bulk sort_order update
  POST /studio/hero-assets/           image upload (multipart)

CACHING:
  Redis keys: viral_products (15m), featured_products (30m),
  public_site_settings (5m) — invalidated on writes.
  HTTP: Cache-Control with s-maxage + stale-while-revalidate on public GETs.

6. HERO BUILDER STUDIO (flagship feature)
--------------------------------------------------------------------------------
URL: /studio/hero (staff login required; non-staff → redirected to login)

WHAT IT IS: a visual page-builder for the homepage hero. Slides are stored as
versioned JSON DOCUMENTS (never HTML). React renders the JSON — the same
renderer serves the storefront and the editor's live preview.

DOCUMENT SCHEMA (per slide, stored in HeroSlide.document JSONField):
  {
    version: 1,
    background: { color, opacity, hexColor, starColor },
    image:      { assetId, url, alt, showOnMobile, mobileOpacity },
    badge:      { enabled, text, bgColor, textColor, borderRadius,
                  fontSize, paddingX, paddingY },
    title:      <native Tiptap JSON>,     // rich text
    subtitle:   { text, color },
    description:{ text, color },
    promo:      <Tiptap JSON> | null,
    buttons:    [ { id, text, link, style:{ bg, color, borderColor,
                    borderRadius, fontSize, fontWeight, paddingX, paddingY,
                    shadow, width, height, hover:{opacity, translateY} } } ]
  }

EDITOR CAPABILITIES:
  • Slide list: live-rendered card thumbnails, add / edit / delete,
    drag-to-reorder (persists via reorder API)
  • Background: color pickers (portal-rendered, never clipped) + opacity
  • Hero image: upload / replace / remove (+ per-slide mobile visibility
    toggle and mobile opacity slider)
  • Badge: full styling controls
  • Main Title & Promo: custom Tiptap editor with toolbar —
    Bold/Italic/Underline, text color, GRADIENT text, highlight, alignment,
    font family, font weight, font size; per-word/character styling
  • Button Builder: unlimited buttons, every style property editable,
    add/delete/drag-reorder, hover controls
  • LIVE PREVIEW: right-hand pane re-renders on every keystroke
  • Save → PATCH API → on-demand ISR revalidate → storefront updates instantly

DATA MODELS: HeroSlide (name, document, schema_version, is_active, sort_order,
valid_from/to for future scheduling) + HeroAsset (uploaded images).
The original 3 static slides were ported into documents via a data migration
(store_settings 0005) so the storefront looked identical after the switch.

FUTURE-READY BY DESIGN: animation presets, video backgrounds, per-breakpoint
overrides, scheduling and i18n can all be added inside the document schema
without DB migrations.

9. RUNNING LOCALLY
--------------------------------------------------------------------------------
Prereqs already on this machine: PostgreSQL 16 + Redis as systemd services
(auto-start on boot). Env files: backend/.env (DB/Redis on localhost),
frontend/.env.local (API at localhost:8000).

EASIEST:  ./start-lan.sh
  → Django on 0.0.0.0:8000 + Next.js on 0.0.0.0:3000
  → uses mDNS hostname so phones on the same Wi-Fi can browse:
       http://tanmoy-ubuntu-computer.local:3000

MANUAL:
  cd backend && source venv/bin/activate && python manage.py runserver
  cd frontend && npm run dev

URLS:
  Storefront      http://localhost:3000
  Hero Studio     http://localhost:3000/studio/hero      (staff login)
  API             http://localhost:8000/api/v1/
  Django admin    http://localhost:8000/admin/
  Staff panel     http://localhost:8000/panel/

NOTE (LAN mode): always open the SAME host the frontend was started with
(the .local hostname) — auth cookies are host-bound, so mixing
localhost/127.0.0.1 with the .local host breaks login.

--------------------------------------------------------------------------------
11. SECURITY
--------------------------------------------------------------------------------
  • JWT in HttpOnly cookies (XSS-safe), refresh rotation + blacklist
  • CSRF: SameSite=Lax cookies; CORS locked to known origins
  • django-axes login lockout; DRF throttling; Django ORM only (no raw SQL)
  • React auto-escaping + zero dangerouslySetInnerHTML in hero rendering
  • Secrets live only in .env files (gitignored — never pushed)


--------------------------------------------------------------------------------
12. NOTEWORTHY ENGINEERING DETAILS
--------------------------------------------------------------------------------
  • WYSIWYG guarantee: one shared <HeroSlideView> renders both the storefront
    hero and the Studio preview — preview can never drift from production.
  • Layout-shift-proof hero: all slides render stacked in one grid cell, so
    the section height is the max of all slides (no jump on slide change);
    image column heights are fixed per breakpoint.
  • Image "dissolve": hero photos fade out via CSS mask-image toward the
    bottom + a strengthened overlay — no visible hem line ever.
  • Featured/viral de-dup is enforced server-side in the featured endpoint.
  • On-demand ISR: Studio saves call /api/revalidate → home updates instantly
    while normal visitors still get fast cached pages.
  • Service worker never caches /studio or /_next assets (stale-bundle guard).
